# تصمیم‌های مقاوم‌سازی

## STEP 01 — حفاظت از اسرار

- پاک‌سازی باید در مرز خروجی (نتیجه، گزارش، JSON مدل و خطای HTTP) انجام شود؛ مخفی‌بودن فیلد credentials به‌تنهایی کافی نیست.
- مقدار واقعی راز فقط از اتصال همان عملیات گرفته می‌شود و به‌صورت سراسری در singleton نگهداری نمی‌شود.
- پاک‌سازی سابقهٔ موجود با فرمان جداگانه انجام می‌شود؛ حالت پیش‌فرض dry-run است و نوشتن نیازمند `--apply` است.
- فرمان تاریخچه فقط error، داده‌های گزارش‌شده و metadata اتصال را هدف می‌گیرد و content انتشار را بازنویسی نمی‌کند.
- گزارش‌گیری و exception handler سراسری متعلق به میزبان است؛ پکیج راهنمای ادغام امن می‌دهد و ادعای پوشش آن مسیر را نمی‌کند.

## STEP 02 — جداسازی شعب و زمینهٔ صف

- زمینهٔ نبود شعبه به معنی دسترسی به رکوردهای global نیست؛ query عملیاتی بدون branch ID رد می‌شود.
- اتصال و انتشار باید متعلق به همان branch ID زمینه باشند. اتصال global تنها با ورود صریح به system context قابل استفاده است.
- `BranchScope` انتخاب صریح شعبهٔ دیگر را هم رد می‌کند؛ `runAsSystem` و `runForBranch` با `try/finally` زمینه را موقت می‌کنند.
- Job انتشار context را از publication ذخیره‌شده می‌گیرد؛ فرمان‌های زمان‌بند برای جست‌وجوی بین‌شعبه‌ای system context صریح دارند.
- مخزن محصول برای عملیات انتشار باید branch را صریح دریافت کند. قرارداد قدیمی ProductRepository نگه داشته شد و قابلیت امن به‌صورت BranchScopedProductRepository افزوده شد.
- adapterهای آرایه‌ای داده را بر پایهٔ branch فیلتر می‌کنند و cache مشترک میان contextها ندارند.

## STEP 03 — دریافت امن رسانه

- resolver عمومی رسانه فقط HTTP(S) بدون credential را می‌پذیرد، تمام پاسخ‌های DNS را از محدودهٔ خصوصی/رزروشده رد می‌کند و اتصال را با `CURLOPT_RESOLVE` به IPهای بررسی‌شده مقید می‌کند.
- redirect خاموش است؛ فایل با `sink` به فایل موقت نوشته می‌شود، سقف اندازه از `omnichannel.media.max_bytes` می‌آید و MIME واقعی با `fileinfo` سنجیده می‌شود.
- قرارداد `MediaBytesResolverContract` حفظ شده است؛ بنابراین پس از دریافت موفق، حداکثر همان سقف بایت در خروجی رشته‌ای لازم می‌شود.
- adapter میزبان مسیرهای محلی را به realpath ریشه‌های public محدود می‌کند و فایل‌های خارج از ریشه، بزرگ یا غیرتصویری/ویدیویی را رد می‌کند.

## STEP 04 — جلوگیری از ارسال تکراری

- کلیدهای جدید نسخه‌دارند و connection، branch مؤثر، محصول، نوع، محتوای canonical، زمان UTC و در `allowDuplicate` شناسهٔ intent را شامل می‌شوند. کلید الگوریتم قدیمی برای یافتن رکوردهای پیشین حفظ می‌شود.
- HTTP retry به‌صورت پیش‌فرض خاموش است؛ فقط caller صریحاً عملیات safe را علامت می‌زند. هیچ درایوری بدون پشتیبانی مستند پلتفرم، کلید idempotency خارجی فرض نمی‌کند.
- نتیجهٔ مبهم کلاس/وضعیت جدا و غیرقابل retry خودکار دارد. `retry()` معمولی آن را رد می‌کند؛ تأیید آگاهانه با پارامتر `confirmUnknownOutcome` و log مستقل انجام می‌شود.
- شناسه‌های مراحل چندمرحله‌ای ابتدا در metadata انتشار پایدار می‌شوند و سپس در cache قرار می‌گیرند. موفقیت Published در پایگاه داده منبع اصلی جلوگیری از ارسال دوباره است.
- فقط claim شرطی اتمیک و رفتارهای پوشش‌داده‌شده تضمین می‌شوند؛ exactly-once برای سرویس خارجی ادعا نمی‌شود.

## STEP 05 — ماشین وضعیت انتشار

- انتقال وضعیت با مقدار status خوانده‌شده از DB شرط می‌شود؛ انتقال Publishing به علاوه به `attempt_token` همان مالک نیاز دارد. تعارض، با خطای صریح رد می‌شود و روی دادهٔ جدید overwrite نمی‌کند.
- هر Job انتشار UUID مالک خود را دارد و claim آن را ثبت می‌کند؛ publish مستقیم نیز token می‌سازد. شمارنده با `attempts + 1` در خود DB افزایش می‌یابد. ستون token nullable است تا migration برای سابقه‌های قدیمی backfill نخواهد.
- رویدادهای Published/Failed پس از تراکنش کوتاه ثبت log و نتیجه dispatch می‌شوند. درخواست خارجی پیش از این تراکنش و بیرون هر تراکنش DB اجرا می‌شود.
- رکورد Publishing قدیمی فقط قابل شناسایی است؛ عمر رکورد به‌تنهایی مجوز retry نیست. callback صف با token job مالکیتش را اثبات می‌کند و در صورت تطابق، نتیجه را UnknownOutcome می‌کند.
- وضعیت Deleted پس از موفقیت API حذف ثبت می‌شود؛ جزئیات حذف در metadata باقی می‌ماند. پاک‌سازی کامل تاریخچه و هم‌زمانی چند درخواست حذف به STEP 07 واگذار شده است.
- آزمون‌های خودکار روی SQLite هستند. قفل/رقابت چندپردازه و migration روی MySQL/PostgreSQL باید در STEP 09 بررسی شوند.

## STEP 06 — ویرایش امن محتوای تأییدشده

- proposal روی clone ساخته و اعتبارسنجی می‌شود؛ Publication تا موفقیت قطعی API محتوای تأییدشده را حفظ می‌کند.
- `ChannelCapabilities` فیلدهای قابل Update و پاک‌کردن را اعلام می‌کند. قابلیت‌های درایورهای بومی محافظه‌کارانه تنظیم شده‌اند.
- `content_version` و قفل مالکیت مشترک Update/Delete از overwrite شدن نتیجهٔ قدیمی جلوگیری می‌کنند.
- شکست قطعی یا نامشخص proposal را در `metadata.omnichannel.content_sync` ثبت می‌کند؛ UnknownOutcome موفقیت تلقی نمی‌شود.
- درخواست خارجی بیرون تراکنش اجرا می‌شود؛ ثبت نتیجه و پایان log در تراکنش کوتاه است. تطبیق خودکار پاسخ خارجیِ ثبت‌نشده وجود ندارد.

## STEP 07 — حذف و نگهداری تاریخچه

- حذف واقعی و غیرفعال‌سازی مسیر جدا دارند. برای driverهای دارای قابلیت Deactivate، قرارداد اختیاری `DeactivatableChannelDriver` و متد سرویس `deactivate()` استفاده می‌شود؛ محصول غیرفعال‌شده status Published دارد.
- آلبوم Bot API شناسه اصلی را در `external_id` حفظ می‌کند و مجموعه کامل را در artifact metadata ذخیره می‌کند. پس از حذف ناقص، فهرست شناسه‌های باقی‌مانده منبع retry است؛ اعضای آلبوم قدیمی حدس زده نمی‌شوند.
- تاریخچه با قید restrict برای channel/connection دارای publication و `nullOnDelete` برای logهای publication حفظ می‌شود. اتصال دارای سابقه باید غیرفعال شود، نه اینکه cascade پاک شود.
- migration upgrade برای MySQL/PostgreSQL قیدها را تغییر می‌دهد؛ SQLite نمی‌تواند قید نام‌دار را درجا تغییر دهد و مسیر ارتقای SQLite نیازمند رسیدگی در STEP 09 است.
- ماتریس رفتار ۹ درایور در `CHANNEL-CAPABILITIES.md` نگه‌داری می‌شود. آن سند snapshot کد است و جایگزین آزمون زنده یا مستند رسمی API نیست.
- WhatsApp Catalog batch، asynchronous (ناهمگام) است: 2xx/handle را موفقیت نهایی نمی‌گیریم؛ handle، زمان و پاسخ پاک‌سازی‌شده در artifact پایدار می‌رود، نتیجه UnknownOutcome می‌شود و هر mutation دیگر مسدود می‌ماند تا reconciliation (تطبیق وضعیت) تکمیل شود. منبع رسمی و تاریخ بررسی در `CHANNEL-CAPABILITIES.md` ثبت شده است.

## STEP 08 — سیاست retry زمان‌دار

- `Retry-After` (عدد ثانیه یا HTTP-date) بر fallback داخلی اولویت دارد؛ زمان انتظار سرور کوتاه نمی‌شود و jitter فقط به آن اضافه می‌شود.
- مهلت job از لحظهٔ ساخت ثابت است تا retryهای یک job پنجره را تمدید نکنند. jobهای قدیمی بدون deadline ذخیره‌شده برای سازگاری یک مهلت runtime می‌گیرند.
- backoff خالی یا نامعتبر به مقادیر پیش‌فرض امن برمی‌گردد. مقدارهای retry و وضعیت پوشش driverها در `RETRY-POLICY.md` ثبت می‌شوند.
- برای dispatch زمان‌بندی‌شده، reservation cache بر مبنای publication و timestamp موعد گذاشته می‌شود؛ job همان timestamp را قبل از publish با DB تطبیق می‌دهد. اشتراک cache بین schedulerها و عمر TTL بخشی از پیکربندی عملیاتی است.
- تمدید token در Basalam و Instagram با lock cache مبتنی بر connection id سریالی می‌شود؛ پس از lock، connection تازه خوانده می‌شود و اگر worker قبلی توکن/انقضا را تغییر داده باشد refresh تکرار نمی‌شود. lock backend باید بین workerها مشترک باشد.
- تصمیم هنوز باز است که throttle باید برای هر درخواست واقعی و بر مبنای حساب/پلتفرم باشد؛ bucket فعلی job-based است و quota رسمی API نیست.
