# امنیت اسرار Omnichannel

## نگهداری و مشاهده

- اعتبارنامه‌های اتصال با cast رمزگذاری‌شدهٔ Laravel ذخیره می‌شوند و در JSON اتصال نمایش داده نمی‌شوند.
- گزارش‌ها، پیام‌های خطا، نتیجه‌های API و JSON مدل‌ها پیش از خروجی‌دادن از پاک‌کنندهٔ ساخت‌یافته عبور می‌کنند. هنگام ثبت عملیات، مقدارهای محرمانهٔ اتصال همان عملیات نیز در حافظه و فقط برای همان پاک‌سازی استفاده می‌شوند.
- پاسخ HTTP فقط پس از پاک‌سازی و محدودشدن اندازه برای گزارش قابل استفاده است؛ payload خام را مستقیماً log نکنید.
- تاریخچهٔ قدیمی را ابتدا با `php artisan omnichannel:redact-history` مرور کنید. برای نوشتن دادهٔ پاک‌شده، فرمان را با `--apply` اجرا کنید. خروجی فرمان فقط نوع رکورد و شمارش را نشان می‌دهد.
- پاک‌سازی بر پایهٔ نام کلید، نشانگرهای متنی رایج، نشانی‌های سرویس‌های پشتیبانی‌شده و اسرار اتصالِ معلوم عمل می‌کند. هرگز credential را داخل پیام خطا یا metadata قرار ندهید.

## گزارش‌گیری میزبان

پکیج کنترل‌کنندهٔ exception و logger سراسری میزبان نیست. میزبان باید پیش از ارسال دادهٔ exception به log، سرویس گزارش‌گیری یا پاسخ Livewire، پیام را با `SecretRedactor::redactString()` پاک کند؛ URL درخواست را بدون query ثبت کند و body/headerهای احراز هویت را حذف کند. حالت debug نیز نباید پیام خام استثنا را به کاربر برگرداند. تنظیم گزارش‌گیر میزبان در این مرحله تغییر نکرده و باید در آزمون ادغام میزبان جداگانه تأیید شود.

## آزمون

مجموعهٔ عادی از credential واقعی پلتفرم استفاده نمی‌کند. تست‌های مرحلهٔ ۰۱ از رازهای ساختگی استفاده می‌کنند و خروجی مدل، گزارش و فرمان تاریخچه را بررسی می‌کنند.

## جداسازی شعب

- عملیات انتشار به زمینهٔ معتبر شعبه نیاز دارند؛ نبود زمینه و اتصال/انتشار شعبهٔ دیگر با `BranchAccessDeniedException` رد می‌شود.
- اتصال‌های بدون `branch_id` فقط در زمینهٔ system صریح قابل‌استفاده‌اند. عملیات عادی شعبه آن‌ها را به‌عنوان اتصال مشترک به ارث نمی‌برد.
- Queryهای `forBranch()` فقط همان شعبه را برمی‌گردانند. انتخاب صریح شعبهٔ دیگری نیازمند زمینهٔ system است.
- مخزن محصولی که برای انتشار استفاده می‌شود باید `BranchScopedProductRepository` را پیاده کند تا جست‌وجوی محصول با branch ID انجام شود.
- Job انتشار، context را به شعبهٔ رکورد محدود می‌کند و در `finally` مقدار قبلی را برمی‌گرداند. فرمان‌های سراسری زمان‌بند تنها مسیرهای مجاز برای `runAsSystem` هستند.
- میزبان باید branch ID معتبر را به `BranchContextResolverContract` بدهد. `ShopProductRepository` میزبان در نبود شعبه خطا می‌دهد و global productها را به همهٔ شعبه‌ها نمایش نمی‌دهد.

## دریافت رسانه

- دریافت HTTP رسانه فقط با نشانی HTTP(S)، بدون credential، و با پاسخ مقصد DNS عمومی انجام می‌شود؛ همهٔ IPهای resolve‌شده بررسی و اتصال به همان مقصدها pin می‌شود تا DNS rebinding نتواند مقصد را عوض کند.
- redirect خاموش است. داده به فایل موقت stream می‌شود، سقف `OMNICHANNEL_MEDIA_MAX_BYTES` (پیش‌فرض ۵۰ MiB) دارد، نوع واقعی با `fileinfo` بررسی می‌شود و فایل موقت در همهٔ مسیرها پاک می‌شود.
- adapter میزبان فقط فایل داخل ریشهٔ واقعی public disk یا public path را می‌خواند؛ symlink خارج از ریشه رد می‌شود و همان سقف اندازه و MIME اعمال می‌شود.
- نوع‌های مجاز پیش‌فرض `image/*` و `video/*` هستند. میزبان می‌تواند با `omnichannel.media.allowed_mime_types` آن را محدودتر کند.

## انتشار تکراری و نتیجه مبهم

- کلید نسخهٔ ۲ قصد انتشار را با اتصال، شعبهٔ مؤثر، محصول، نوع، محتوای استاندارد، زمان زمان‌بندی‌شده در UTC و شناسهٔ نیت (در بازانتشار آگاهانه) می‌سازد. کلیدهای قدیمی قبل از ایجاد رکورد جدید جست‌وجو می‌شوند تا سوابق موجود دوباره منتشر نشوند.
- retry خودکار HTTP پیش‌فرض خاموش است. فقط عملیاتی که مصرف‌کننده صریحاً `retrySafe: true` اعلام کند از سیاست retry استفاده می‌کنند؛ این کار برای POST تنها با پشتیبانی idempotency مستند پلتفرم مجاز است.
- قطع ارتباط، timeout، پاسخ ۵xx یا پاسخ انتشار بدون شناسهٔ پایدار به `unknown_outcome` می‌رود و خودکار دوباره ارسال نمی‌شود. retry دستی این وضعیت به `confirmUnknownOutcome: true` نیاز دارد و مجوز آن در log ثبت می‌شود.
- artifactهای ضروری انتشار، شناسهٔ پیام/فایل/کانتینر، ابتدا در metadata رکورد انتشار ذخیره می‌شوند و cache فقط میانبر است. وضعیت Published پایگاه داده نیز مستقل از cache، تکرار انتشار موفق را مسدود می‌کند.
- API تطبیق خودکار وضعیت کانال در همهٔ پلتفرم‌ها وجود ندارد؛ در این موارد سابقه را بررسی کنید و ارسال دوباره را آگاهانه تأیید کنید. exactly-once تضمین نمی‌شود.

## مالکیت تلاش و وضعیت انتشار

- claim انتشار با UPDATE شرطی انجام می‌شود؛ شمارنده تلاش از نمونهٔ مدل خوانده نمی‌شود و در پایگاه داده افزایش می‌یابد.
- `attempt_token` داخلی مالک جاری را مشخص می‌کند، در JSON مدل پنهان است و نتیجهٔ پردازشگر قدیمی را از تغییر وضعیت تلاش جدید بازمی‌دارد.
- رکورد Publishing متوقف خودکار به Failed یا صف قابل‌ارسال برنمی‌گردد. query `stuckInFlight` فقط برای بررسی عملیاتی است؛ زمان سپری‌شده به معنی شکست قطعی نیست.
- نتیجهٔ انتشار و پایان log در یک تراکنش کوتاه ذخیره می‌شوند. event پس از commit منتشر می‌شود و درخواست شبکه در تراکنش DB اجرا نمی‌شود.

## ویرایش امن محتوای منتشرشده

- proposal ویرایش روی clone اعتبارسنجی می‌شود؛ اعتبارسنجی ناموفق پیش از درخواست خارجی برمی‌گردد.
- قابلیت هر فیلد از driver خوانده می‌شود. تغییر رسانه یا فیلد unsupported به‌جای موفقیت ناقص، رد می‌شود.
- Update و Delete با مالکیت شرطی مشترک اجرا می‌شوند؛ نسخهٔ محتوای claim شده نیز شرط نوشتن نتیجه است.
- محتوای تأییدشده فقط پس از موفقیت خارجی جایگزین می‌شود. شکست قطعی یا نامشخص proposal و وضعیت sync را ثبت می‌کند و محتوای قبلی را حفظ می‌کند.
- نتیجهٔ نامشخص با موفقیت یکی نیست و proposal آن برای بررسی نگه داشته می‌شود.

## حذف و تاریخچهٔ کانال

- عملیات remote delete وضعیت Deleted را فقط پس از تأیید ثبت می‌کند و شناسه‌های خارجی را در metadata نگه می‌دارد.
- غیرفعال‌سازی فهرست با Delete یکی نیست؛ اتصال و publication باقی می‌مانند و عملیات جداگانه log می‌شود.
- حذف channel/connection دارای publication با قید پایگاه داده متوقف می‌شود. log پس از حذف publication بدون والد باقی می‌ماند.
- مجموعه شناسه‌های آلبوم کامل و پایدار است؛ پس از حذف ناقص فقط اعضای باقی‌مانده هدف گرفته می‌شوند. برای رکورد قدیمی شناسهٔ گمشده ساخته نمی‌شود.
