اقدامات:

1. رفتار strict و inherit_global را با نیاز واقعی میزبان تطبیق بده.
2. در صورت نیاز به اتصال عمومی، مجوز استفاده از اتصال عمومی را از مجوز مدیریت آن تفکیک کن.

5. کلید قدیمی نباید زمان‌بندی مستقل جدید یا انتشار شعبه دیگر را ناخواسته مسدود کند.
6. دسترسی عملیات بر اساس اطلاعات معتبر و تازه پایگاه داده بررسی شود.
7. کنترل تطابق channel، connection و publication تکمیل شود.
8. جداسازی لاگ‌ها و رابط‌های میزبان بررسی شود.
9. Actor ID و مجوز اجرای system context از ورودی غیرقابل اعتماد دریافت نشوند.

### ۱.۳. تکمیل امنیت رسانه

فایل:

`src/Http/HttpMediaBytesResolver.php`

مشکلات قابل بررسی:

- پرچم‌های NO_PRIV_RANGE و NO_RES_RANGE به‌تنهایی تمام محدوده‌های غیرعمومی را پوشش نمی‌دهند.
- نحوه ساخت CURLOPT_RESOLVE برای IPv6 صحیح نیست؛ جداکننده‌های آدرس حذف می‌شوند.
- بازگرداندن boolean از progress callback لزوماً توقف واقعی دانلود را تضمین نمی‌کند.
- HTTP Fake رفتار انتقال واقعی را به‌طور کامل شبیه‌سازی نمی‌کند.

اقدامات:

1. اعتبارسنجی IP عمومی با سیاست معتبر و کامل انجام شود.
2. IPv4، IPv6، CGNAT، link-local، mapped addresses و محدوده‌های رزروشده بررسی شوند.
3. DNS pinning با ساختار صحیح IPv6 انجام شود.
4. استفاده از proxy یا HTTP handler فاقد پشتیبانی pinning نباید محافظت را دور بزند.
5. محدودیت حجم هنگام نوشتن جریان داده اعمال شود، نه صرفاً پس از پایان دانلود.
6. حجم واقعی داده، داده فشرده‌شده، پاسخ بدون Content-Length و دانلود ناقص بررسی شوند.
7. خطای دانلود باعث پاک شدن فایل موقت شود.
8. مسیر محلی میزبان در برابر Path Traversal و Symlink Escape تست شود.
9. محافظت TLS حفظ شود.

### ۱.۴. نتیجه نامشخص ویرایش

در `finishContentUpdateFailure` بررسی کن که نتیجه نامشخص باعث آزاد شدن مالکیت عملیات و امکان اجرای تغییر جدید قبل از تطبیق وضعیت نشود.

سیاست نتیجه نامشخص باید برای Publish، Update، Delete و Deactivate منسجم باشد.

### ۱.۵. رقابت زمان‌بندی

زمان‌بندی، نسخه برنامه و شرایط مجاز انتشار باید در تصاحب اتمیک رکورد کنترل شوند.

فراخوانی مستقیم publish نیز نباید انتشار Scheduled را پیش از موعد منتشر کند، مگر در مسیر اجرایی صریح و مجاز.

- نصب تازه و ارتقا بدون خطا انجام شوند.
- هیچ رفتار امنیتی مرحله اول تضعیف نشود.

## ۵. STEP 02 — API Request Rate Limiting

اولویت: High

### مشکل

`ThrottleChannelRequests` در حال حاضر تعداد اجرای Job را محدود می‌کند، نه درخواست‌های واقعی API.

یک عملیات انتشار ممکن است چندین درخواست آپلود، ساخت کانتینر، بررسی وضعیت و انتشار ایجاد کند.

### طراحی

محدودکننده Job را از محدودکننده API جدا کن.

ساختار پیشنهادی:

- `ApiRequestRateLimiter`
- `RateLimitPolicy`
- `RateLimitContext`
- `RateLimitExceededException`

نام کلاس‌ها پیشنهادی هستند و باید متناسب با معماری فعلی انتخاب شوند.

### اقدامات

1. تمام درخواست‌های واقعی API را شناسایی کن.
2. محدودکننده را در لایه مشترک HTTP قرار بده.
3. مسیرهایی که از BaseApiClient عبور نمی‌کنند نیز پوشش داده شوند.
4. هر تلاش مجدد واقعی HTTP یک درخواست مستقل محسوب شود.
5. محدودیت بر اساس پلتفرم، حساب خارجی و در صورت نیاز endpoint تعریف شود.
6. چند اتصال متعلق به یک حساب خارجی نتوانند سهمیه را دور بزنند.
7. استفاده از توکن خام در کلید cache ممنوع باشد.
8. رزرو و مصرف سهمیه در اجرای هم‌زمان اتمیک باشد.
9. در صورت نبود cache مشترک مناسب، رفتار امن و هشدار مشخص وجود داشته باشد.
10. محدودیت داخلی پکیج به‌عنوان quota رسمی پلتفرم معرفی نشود.
11. خطای Rate Limit محلی از پاسخ 429 پلتفرم تفکیک شود.
12. زمان انتظار اعلام‌شده پلتفرم در تمام درایورها به سرویس و Job منتقل شود.
13. عملیات مستقیم Update، Delete، Test Connection و Refresh Token نیز تحت سیاست مناسب قرار گیرند.

### تست‌ها

- `ApiRequestRateLimiterTest`
- `ConcurrentRateLimitTest`
- `SharedAccountRateLimitTest`
- `DriverRequestCountingTest`
- `RetryAfterPropagationTest`

### معیار پذیرش

تمام درخواست‌های واقعی، از جمله تلاش‌های مجدد و عملیات چندمرحله‌ای، تحت محدودیت قابل پیکربندی باشند.
