# Phase 01 — Omnichannel Core Hardening

## ۱. نقش و مأموریت

به‌عنوان یک Senior Laravel Package Architect و Backend Security Engineer (معمار ارشد پکیج لاراول و متخصص امنیت بک‌اند) مسئول بررسی، اصلاح و مقاوم‌سازی پکیج زیر هستی:

- Package: `karnoweb/omnichannel`
- Path: `packages/karnoweb/omnichannel`
- Current Version: `13.0.0`
- PHP: `^8.3`
- Laravel / Illuminate: `^13.0`

هدف این مرحله افزایش امنیت، پایداری، یکپارچگی داده‌ها، قابلیت اطمینان و جلوگیری از خطاهای اجرایی پکیج است.

این مرحله توسعه امکانات جدید نیست؛ بلکه Core Hardening (مقاوم‌سازی هسته موجود) است.

## ۲. قوانین غیرقابل نقض معماری

در تمام مراحل پیاده‌سازی قوانین زیر را رعایت کن:

- استقلال کامل پکیج از پروژه میزبان حفظ شود.
- هیچ وابستگی مستقیم به `App\*` یا پکیج‌های Shop، Commerce، CRM، Inventory و Accounting ایجاد نشود.
- ارتباط با میزبان فقط از طریق قراردادها و تنظیمات قابل تزریق انجام شود.
- هیچ کلید خارجی مستقیم به جداول میزبان ایجاد نشود.
- پشتیبانی از کلیدهای `int`، `uuid` و `ulid` حفظ شود.
- معماری Driver-Based (مبتنی بر درایور) حفظ شود.
- منطق اختصاصی پلتفرم‌ها وارد سرویس عمومی انتشار نشود.
- قابلیت‌های درایورها از طریق `ChannelCapabilities` مدیریت شوند.
- تنظیم‌پذیری نام جداول و مدل‌ها حفظ شود.
- هر ۹ درایور فعلی حفظ شوند.
- از بازنویسی کامل پکیج و پیچیدگی غیرضروری خودداری شود.
- سازگاری با مصرف‌کنندگان فعلی پکیج تا حد ممکن حفظ شود.
- استانداردهای نام‌گذاری و ساختار فعلی رعایت شوند.
- ترجمه‌های فارسی و انگلیسی تکمیل شوند.
- اطلاعات حساس در تست‌ها، مستندات و گزارش‌ها قرار نگیرند.
- هیچ تستی برای عبور ظاهری از بررسی‌ها حذف یا تضعیف نشود.

افزودن Unified Inbox، Webhook دریافت پیام، انتشار گروهی، همگام‌سازی خودکار کاتالوگ و درایور جدید در محدوده این مرحله نیست.

## ۴. STEP 01 — Secret Protection

اولویت: Critical (بحرانی)

### مشکل

سیستم `SecretRedactor` وجود دارد، اما تمام مسیرهای افشای اطلاعات حساس را پوشش نمی‌دهد.

برای مثال توکن تلگرام در ساختار مسیر `bot<TOKEN>/sendMessage` قرار می‌گیرد و ممکن است در پیام خطای ارتباطی ذخیره شود.

همچنین برخی پیام‌های خطا مستقیماً در مدل‌ها ذخیره می‌شوند.

### فایل‌های اصلی

- `src/Services/SecretRedactor.php`
- `src/Services/PublicationLogger.php`
- `src/Services/PublishingService.php`
- `src/Http/BaseApiClient.php`
- `src/Http/ApiResponse.php`
- `src/Models/Publication.php`
- `src/Models/ChannelConnection.php`
- `src/Jobs/PublishPublicationJob.php`
- `src/Channels/*/*Authenticator.php`
- `src/Results/`

### راه‌حل

1. سیستم حذف اطلاعات حساس را برای موارد زیر تکمیل کن:

   - Bearer Token
   - Basic Authentication
   - Bot Token در مسیر URL
   - Access Token
   - Refresh Token
   - API Key
   - Client Secret
   - OAuth Authorization Code
   - Cookie
   - Authorization Header
   - اطلاعات حساس داخل JSON
   - اطلاعات حساس داخل خطاهای شبکه
   - مقادیر رمزگذاری‌شده در URL
   - اطلاعات حساس داخل آرایه‌های تودرتو

2. علاوه بر الگوهای عمومی، امکان حذف مقادیر واقعی اعتبارنامه اتصال از متن خطا را به‌صورت محدود به همان عملیات فراهم کن.

3. اطلاعات حساس را قبل از ورود به قسمت‌های زیر پاک‌سازی کن:

   - `error_message`
   - `status_message`
   - Publication Logs
   - Laravel Logs
   - Exception Messages
   - Event Payloads
   - Result Objects
   - Response Metadata

4. اطلاعات پاسخ خام سرویس خارجی را فقط به اندازه ضروری و پس از پاک‌سازی ذخیره کن.

5. محدودیت حجم لاگ را پس از پاک‌سازی اعمال کن.

6. بررسی کن ابزارهای گزارش خطای میزبان و گزارش درخواست‌های HTTP نیز باعث افشای اعتبارنامه نشوند.

7. رمزنگاری فعلی `credentials` و مخفی‌بودن آن هنگام تبدیل مدل به JSON حفظ شود.

8. برای پاک‌سازی سوابق قدیمی آلوده، یک فرمان مدیریتی امن با حالت `dry-run` (اجرای آزمایشی بدون تغییر داده) طراحی کن. هیچ توکن واقعی را در خروجی آن نمایش نده.

9. در صورت وجود شواهد افشای واقعی، نیاز به تعویض توکن را گزارش کن.

### تست‌های ضروری

- `SecretRedactorTest`
- `PublicationLoggerSecurityTest`
- `SensitiveExceptionTest`

### معیار پذیرش

- توکن آزمایشی تلگرام در URL به‌درستی حذف شود.
- اطلاعات حساس در آرایه‌های تودرتو حذف شوند.
- خطای شبکه حاوی توکن وارد پایگاه داده یا لاگ نشود.
- خروجی Result و رویدادهای انتشار توکن خام نداشته باشند.
- اعتبارنامه مورد نیاز برای ارتباط واقعی با پلتفرم دست‌نخورده باقی بماند.

## ۵. STEP 02 — Branch Isolation

اولویت: Critical (بحرانی)

### مشکل

`BranchScope` یک Local Scope (فیلتر اختیاری درخواست پایگاه داده) است.

در نتیجه عملیات سرویس‌ها لزوماً محدود به شعبه فعلی نیستند. همچنین شناسه شعبه در کلید جلوگیری از تکرار انتشار لحاظ نشده است.

### فایل‌های اصلی

- `src/Support/BranchScope.php`
- `src/Support/OmnichannelContext.php`
- `src/Contracts/BranchContextResolverContract.php`
- `src/Services/PublishingService.php`
- `src/Services/IdempotencyKeyGenerator.php`
- `src/Models/Publication.php`
- `src/Models/ChannelConnection.php`
- `src/Models/PublicationLog.php`
- `src/Jobs/PublishPublicationJob.php`
- `src/Console/`

### راه‌حل

1. یک لایه مرکزی برای اعتبارسنجی دسترسی به شعبه طراحی کن؛ برای مثال:

   `BranchAccessGuard`

2. تمام متدهای عمومی عملیاتی را تحت کنترل این لایه قرار بده:

   - `create`
   - `publish`
   - `update`
   - `delete`
   - `schedule`
   - `cancel`
   - `retry`
   - `testConnection`

3. دسترسی به شعبه را بر اساس Context (زمینه اجرایی معتبر) تعیین کن؛ نه یک شناسه شعبه که مستقیماً توسط کاربر ارسال شده است.

4. رفتار دو حالت موجود باید شفاف باشد:

   **Strict:**

   هر شعبه فقط به رکوردهای متعلق به همان شعبه دسترسی دارد.

   **Inherit Global:**

   شعبه می‌تواند از اتصال عمومی مجاز استفاده کند، اما این موضوع نباید مجوز مشاهده یا مدیریت انتشار شعب دیگر را ایجاد کند.

5. امکان استفاده از اتصال عمومی را از مجوز ویرایش و حذف خود اتصال تفکیک کن.

6. نبود Branch Context نباید به معنی دسترسی نامحدود باشد.

7. اجرای Scheduler (زمان‌بند) و Queue Worker (پردازشگر صف) باید از مسیر اجرایی سیستمی مشخص و قابل کنترل انجام شود.

8. هنگام اجرای Job، رکورد انتشار و اتصال را مجدداً از پایگاه داده دریافت و اعتبارسنجی کن.

9. زمینه اجرایی شعبه در پردازشگرهای طولانی‌مدت نباید به Job بعدی منتقل شود.

10. دسترسی به PublicationLog از طریق انتشار یا اتصال مرتبط کنترل شود.

11. شناسه شعبه مؤثر در تولید Idempotency Key لحاظ شود.

12. شرایط عدم تطابق شعبه انتشار، شعبه اتصال و شناسه کانال را شناسایی و مسدود کن.

13. از ایجاد Global Scope (فیلتر سراسری خودکار) بدون بررسی اثر آن بر زمان‌بند، صف و روابط مدل‌ها خودداری کن.

14. کنترل دسترسی به محصول در شعبه از طریق قراردادهای میزبان انجام شود، نه وابستگی مستقیم به مدل‌های فروشگاه.

### تست‌های ضروری

- `BranchIsolationTest`
- `GlobalConnectionIsolationTest`
- `CrossBranchPublicationTest`
- `BranchAwareQueueTest`
- `PublicationLogIsolationTest`

### معیار پذیرش

- شعبه A نتواند انتشار شعبه B را تغییر دهد.
- شعبه A نتواند اتصال اختصاصی شعبه B را استفاده کند.
- انتشار یک محصول از دو شعبه با اتصال عمومی، با یکدیگر تداخل نداشته باشد.
- دسترسی مستقیم با ارسال نمونه مدل متعلق به شعبه دیگر مسدود شود.
- زمان‌بند و صف همچنان بتوانند انتشارهای مجاز تمام شعب را پردازش کنند.
- انواع کلید `int`، `uuid` و `ulid` بدون مشکل کار کنند.

## ۶. STEP 03 — Secure Media Fetching

اولویت: Critical (بحرانی)

### مشکل

`HttpMediaBytesResolver` آدرس رسانه را مستقیماً دانلود می‌کند.

این رفتار خطر SSRF (وادار کردن سرور به ارسال درخواست به منابع داخلی)، دانلود فایل‌های بیش از حد بزرگ و مصرف کنترل‌نشده حافظه را ایجاد می‌کند.

### فایل‌های اصلی

- `src/Http/HttpMediaBytesResolver.php`
- `src/Contracts/MediaBytesResolverContract.php`
- `src/ValueObjects/MediaItem.php`
- `src/Channels/Basalam/BasalamMediaUploader.php`
- درایورهای دارای قابلیت آپلود رسانه
- `config/omnichannel.php`

### راه‌حل

1. یک لایه اعتبارسنجی امن آدرس رسانه ایجاد کن؛ برای مثال `MediaUrlValidator`.

2. فقط پروتکل‌های HTTP و HTTPS مجاز باشند.

3. دسترسی به موارد زیر مسدود شود:

   - Localhost
   - آدرس‌های شبکه خصوصی
   - Loopback
   - Link-local
   - آدرس‌های رزروشده
   - سرویس‌های Cloud Metadata
   - آدرس معادل IPv4 در IPv6
   - آدرس دارای نام کاربری و رمز عبور

4. نام دامنه و آدرس‌های IP حاصل از DNS بررسی شوند.

5. از DNS Rebinding (تغییر مقصد دامنه پس از اعتبارسنجی) با اعتبارسنجی و اتصال به مقصد تأییدشده جلوگیری کن.

6. Redirect (تغییر مسیر HTTP) به‌صورت پیش‌فرض غیرفعال باشد. در صورت نیاز، هر مقصد جدید مجدداً اعتبارسنجی شود.

7. تعداد تغییر مسیرها محدود باشد.

8. محدودیت حجم واقعی فایل هنگام دانلود اعمال شود؛ به `Content-Length` به‌تنهایی اعتماد نکن.

9. دانلود به‌صورت Streaming (دریافت تدریجی داده) و با سقف حجم مشخص انجام شود.

10. نوع واقعی رسانه و MIME Type (نوع محتوای فایل) بررسی شوند.

11. تنظیمات زیر به‌صورت قابل پیکربندی تعریف شوند:

   - حداکثر حجم تصویر
   - حداکثر حجم ویدیو
   - زمان اتصال
   - زمان دانلود
   - نوع فایل مجاز
   - دامنه‌های مجاز در صورت نیاز
   - تعداد تغییر مسیرها

12. هنگام خطا فایل‌های موقت پاک شوند.

13. اعتبارسنجی گواهی TLS (ارتباط رمزنگاری‌شده) غیرفعال نشود.

14. قرارداد فعلی دریافت رسانه تا حد ممکن حفظ شود تا `HostMediaBytesResolver` دچار اختلال نشود.

15. در صورت وجود خواننده اختصاصی در میزبان، مسیر خواندن فایل محلی و مسیر دانلود HTTP از نظر امنیت بررسی و مستند شوند.

### تست‌های ضروری

- `MediaUrlValidatorTest`
- `MediaSsrfProtectionTest`
- `MediaDownloadLimitTest`
- `MediaRedirectSecurityTest`

### معیار پذیرش

- دریافت رسانه عمومی معتبر موفق باشد.
- آدرس داخلی و خصوصی مسدود شود.
- تغییر مسیر از دامنه معتبر به شبکه داخلی مسدود شود.
- فایل بزرگ‌تر از حد مجاز حتی بدون Content-Length دریافت نشود.
- فایل نامعتبر یا دانلود ناقص باعث پردازش انتشار نشود.

## ۷. STEP 04 — Reliable Idempotency

اولویت: Critical (بحرانی)

### مشکل

Idempotency (جلوگیری از اجرای تکراری یک عملیات) فعلی چند لایه دارد، اما انتشار تکراری در شرایط قطع ارتباط همچنان ممکن است.

`BaseApiClient` ممکن است پس از خطای ارتباطی، درخواست ارسال محتوا را مجدداً اجرا کند.

اگر پلتفرم درخواست اول را انجام داده باشد ولی پاسخ به سرور نرسیده باشد، درخواست دوم می‌تواند محتوای تکراری ایجاد کند.

### فایل‌های اصلی

- `src/Http/BaseApiClient.php`
- `src/Http/ApiResponse.php`
- `src/Services/IdempotencyKeyGenerator.php`
- `src/Services/PublishingService.php`
- `src/Models/Publication.php`
- `src/Enums/FailureClass.php`
- `src/Results/PublishResult.php`
- `src/Channels/`
- `src/Jobs/PublishPublicationJob.php`

### راه‌حل اول: اصلاح Idempotency Key

کلید انتشار باید مفهوم «نیت انتشار» را به شکل مشخص مدل کند.

موارد مؤثر:

- Connection ID
- Effective Branch ID
- Product ID
- Publication Type
- Canonical Content (محتوای استانداردسازی‌شده)
- زمان انتشار اولیه در صورت زمان‌بندی
- Intent Identifier (شناسه نیت انتشار) در صورت نیاز

الزامات:

1. تغییر ترتیب کلیدهای آرایه نباید کلید متفاوت ایجاد کند.
2. تغییر ترتیب رسانه‌ها در آلبوم باید کلید متفاوت ایجاد کند.
3. انتشار یکسان از دو شعبه باید کلید متفاوت داشته باشد.
4. زمان‌های معادل با منطقه زمانی متفاوت باید یکسان تشخیص داده شوند.
5. انتشار آگاهانه مجدد باید کلید مستقل تولید کند.
6. تلاش مجدد برای همان درخواست نباید کلید جدید بسازد.
7. `allowDuplicate` نباید باعث ایجاد چند رکورد در اثر تکرار فنی همان درخواست شود.
8. زمان‌بندی مجدد یک رکورد موجود نباید هویت آن را به‌صورت ناخواسته تغییر دهد.
9. محدودیت یکتایی در سطح پایگاه داده حفظ شود.
10. خطاهای هم‌زمان ایجاد رکورد به شکل کنترل‌شده مدیریت شوند.
11. تغییر الگوریتم کلید نباید باعث انتشار مجدد رکوردهای قدیمی شود. برای سازگاری با کلیدهای نسخه قبلی سیاست مشخص طراحی کن.

### راه‌حل دوم: تفکیک نوع درخواست HTTP

درخواست‌ها را بر اساس رفتار واقعی عملیات دسته‌بندی کن:

- عملیات فقط‌خواندنی
- عملیات قابل تکرار ایمن
- عملیات دارای شناسه پایدار سمت پلتفرم
- عملیات غیرقابل تکرار بدون خطر

فقط بر اساس GET یا POST بودن درخواست درباره ایمنی تکرار تصمیم نگیر.

برای نمونه، برخی درخواست‌های POST صرفاً اطلاعات دریافت می‌کنند و بعضی درخواست‌های GET ممکن است توکن را تمدید کنند.

1. تلاش مجدد خودکار برای عملیات غیرایمن غیرفعال شود.
2. عملیات فقط‌خواندنی بتوانند مطابق سیاست مشخص مجدداً اجرا شوند.
3. عملیات ارسال پیام بدون پشتیبانی واقعی پلتفرم از Idempotency، پس از خطای مبهم نباید خودکار تکرار شوند.
4. در صورت پشتیبانی مستند پلتفرم از شناسه پایدار، از آن استفاده کن.

### راه‌حل سوم: مدیریت نتیجه نامشخص

وضعیتی مستقل معرفی کن که نشان دهد درخواست احتمالاً به پلتفرم رسیده اما نتیجه نهایی مشخص نیست.

نام پیشنهادی:

`UnknownOutcome`

این وضعیت با خطای معمولی `Failed` متفاوت است.

سناریوهای مرتبط:

- قطع ارتباط پس از ارسال درخواست
- Timeout پس از شروع عملیات
- پاسخ موفق بدون شناسه انتشار معتبر
- توقف Worker بعد از انتشار خارجی
- شکست ذخیره نتیجه موفق در پایگاه داده
- خطای مبهم سرویس خارجی

در این شرایط:

- انتشار خودکار مجدد ممنوع باشد.
- سوابق عملیات حفظ شوند.
- ابتدا امکان Reconciliation (تطبیق وضعیت داخلی با وضعیت واقعی پلتفرم) بررسی شود.
- در صورت نبود قابلیت تطبیق، نیاز به بررسی انسانی مشخص شود.
- عملیات ارسال مجدد فقط با تصمیم آگاهانه و ثبت سابقه انجام شود.

### راه‌حل چهارم: ذخیره پایدار نتیجه عملیات

Cache (حافظه موقت) نباید تنها منبع جلوگیری از ارسال تکراری باشد.

برای عملیات چندمرحله‌ای، اطلاعات ضروری مانند شناسه کانتینر، شناسه فایل و شناسه انتشار تا حد امکان به‌صورت پایدار و متناسب با همان تلاش ذخیره شوند.

تمام کلیدهای Cache باید هویت اتصال، انتشار و عملیات را به‌شکل مناسب منعکس کنند.

از داده‌های قدیمی Cache برای یک انتشار آگاهانه جدید استفاده نشود.

## ۸. STEP 05 — Publication State Machine

اولویت: Critical (بحرانی)

### مشکل

چرخه وضعیت انتشار در بعضی مسیرها به‌صورت ناقص مدیریت می‌شود.

متد `failWithoutAttempt` پیام خطا را ذخیره می‌کند، اما وضعیت انتشار را به `Failed` تغییر نمی‌دهد.

علاوه بر این، برخی انتقال وضعیت‌ها بر اساس نمونه قدیمی مدل انجام می‌شوند و در برابر اجرای هم‌زمان مقاوم نیستند.

- `src/Jobs/PublishPublicationJob.php`
- `src/Console/DispatchDuePublicationsCommand.php`

### طراحی پیشنهادی وضعیت‌ها

وضعیت‌های فعلی حفظ شوند:

- Draft
- Scheduled
- Publishing
- Published
- Failed
- Cancelled

وضعیت‌های ضروری جدید بررسی و اضافه شوند:

- UnknownOutcome
- Deleted

غیرفعال‌سازی کاتالوگ و وضعیت همگام‌سازی محتوا می‌توانند وضعیت مستقل داشته باشند تا چرخه انتشار بی‌جهت پیچیده نشود.

### راه‌حل

1. جدول رسمی انتقال وضعیت‌ها ایجاد کن.

2. تمام انتقال‌ها از یک مسیر مشخص و کنترل‌شده عبور کنند.

3. انتقال غیرمجاز مسدود شود.

4. `failWithoutAttempt` اصلاح شود تا انتشار نامعتبر واقعاً وارد وضعیت Failed شود.

5. شکست اعتبارسنجی نباید شمارنده تلاش ارسال واقعی را افزایش دهد.

6. `failed_at`، `failure_class`، `error_code` و پیام خطا به‌درستی ثبت شوند.

7. انتشار Scheduled نامعتبر نباید هر دقیقه دوباره وارد صف شود.

8. هنگام Claim (ادعای مالکیت پردازش)، وضعیت رکورد به‌صورت اتمیک بررسی شود.

9. به‌جای مقدار قدیمی مدل، شمارنده تلاش به‌صورت اتمیک در پایگاه داده افزایش یابد.

10. انتقال‌های حساس مانند Cancel و Schedule نیز در برابر تغییر هم‌زمان وضعیت مقاوم باشند.

11. پردازشگر قدیمی نباید بتواند نتیجه پردازشگر جدیدتر را بازنویسی کند. شناسه تلاش یا مکانیزم مشابه برای تعیین مالکیت عملیات در نظر بگیر.

12. عملیات شبکه را داخل تراکنش طولانی پایگاه داده انجام نده.

13. هنگام موفقیت، ثبت نتیجه انتشار و سوابق ضروری به‌صورت منسجم انجام شود.

14. شکست ثبت لاگ یا اجرای Event نباید باعث انتشار مجدد محتوا شود.

15. Eventها پس از ثبت موفق تراکنش منتشر شوند.

16. انتشارهایی که در وضعیت Publishing متوقف شده‌اند شناسایی شوند. صرفاً به دلیل گذشت زمان به وضعیت قابل تلاش مجدد منتقل نشوند؛ ابتدا خطر انجام شدن عملیات خارجی بررسی شود.

17. ثبت موفق عملیات بدون External ID معتبر نباید وضعیت Published ایجاد کند.

18. سازگاری وضعیت‌های جدید با ترجمه‌ها، رنگ‌ها، آیکون‌ها و مصرف‌کنندگان میزبان بررسی شود.

## ۱۳. Database Migration Policy

در صورت نیاز به تغییر ساختار پایگاه داده:

- Migration فعلی نصب‌شده را بدون برنامه سازگاری بازنویسی نکن.
- تغییرات لازم برای نصب‌های موجود به شکل Migration افزایشی انجام شوند.
- مسیر نصب تازه و بروزرسانی نسخه قبلی هر دو کار کنند.
- از `OmnichannelTables` استفاده شود.
- ساختار کلیدهای نرم میزبان حفظ شود.
- داده‌های قدیمی حذف نشوند.
- Idempotency Keyهای قدیمی بدون برنامه مهاجرت تغییر نکنند.
- وضعیت رکوردهای قبلی بر اساس شواهد واقعی تعیین شوند.
- اطلاعات قدیمی که قابل بازیابی نیستند با اطلاعات ساختگی جایگزین نشوند.
- Migration تا حد امکان قابل Rollback (بازگشت تغییر ساختار) باشد.
- محدودیت بازگشت داده‌های تغییرکرده مستند شود.
- هیچ دستور مخربی مانند `migrate:fresh` روی پایگاه داده عملیاتی اجرا نشود.

## ۱۵. Implementation Workflow

تمام مراحل را به ترتیب زیر انجام بده:

1. تحلیل مشکل و تأیید آن در کد.
2. تعیین فایل‌های تحت تأثیر.
3. ارائه طراحی اصلاح.
4. ایجاد تست بازتولید مشکل.
5. پیاده‌سازی اصلاح.
6. اجرای تست جدید.
7. اجرای تست‌های قبلی.
8. بررسی اثر تغییر بر تمام درایورها.
9. ثبت تغییرات در مستندات.
10. علامت‌گذاری چک‌لیست مرحله.

هر STEP باید مستقل، قابل بررسی و قابل بازگشت باشد.

تغییرات تمام مراحل را در یک Commit بزرگ ترکیب نکن.

پس از پایان هر STEP گزارشی با این ساختار ارائه بده:

- Step
- Problems Confirmed
- Files Created
- Files Modified
- Changes Implemented
- Database Changes
- Breaking Changes
- Tests Added
- Test Results
- Remaining Risks
- Acceptance Criteria Status

اگر محیط اجرای تست در دسترس نیست، تست را به‌عنوان اجراشده یا موفق گزارش نکن.

## ۱۷. Definition of Done

- [ ] هیچ اطلاعات حساس شناخته‌شده‌ای وارد مسیرهای لاگ و خطا نمی‌شود.

- [ ] دانلود رسانه در برابر SSRF و حجم غیرمجاز محافظت شده است.
- [ ] ارسال هم‌زمان باعث انتشار تکراری نمی‌شود.
- [ ] درخواست خارجی با نتیجه نامشخص خودکار تکرار نمی‌شود.
- [ ] وضعیت انتشار نامعتبر به‌درستی ثبت می‌شود.
- [ ] انتقال وضعیت‌های هم‌زمان کنترل شده‌اند.
- [ ] شکست بروزرسانی باعث بازنویسی محتوای تأییدشده نمی‌شود.
- [ ] حذف انتشار و حذف ناقص به‌درستی مدیریت می‌شوند.
- [ ] تمام شناسه‌های خارجی آلبوم حفظ می‌شوند.
- [ ] محدودیت درخواست و سیاست Retry اصلاح شده‌اند.
- [ ] توقف Worker به ارسال مجدد ناامن منجر نمی‌شود.
- [ ] سوابق عملیاتی حفظ شده‌اند.
- [ ] تست‌های جدید و قبلی موفق هستند.
- [ ] هر ۹ درایور از نظر تغییرات هسته بررسی شده‌اند.
- [ ] هیچ وابستگی مستقیم جدیدی به میزبان ایجاد نشده است.
- [ ] نصب جدید و بروزرسانی نسخه موجود بررسی شده‌اند.
- [ ] تمام تغییرات و محدودیت‌ها مستند شده‌اند.
